# Database Schema and Data Ownership

The source of truth is the TypeORM entity/migration code. Schema synchronization is disabled. The current visual/documentation phase adds no business tables. The earlier workspace expansion adds the SQL tables listed in the generated inventory below.

## Ownership and relationships

- `users` ↔ `roles` ↔ `permissions` via join tables; sessions reference a user and contain only hashed session secrets.
- Channel accounts belong to a channel; provider events and messages are uniquely deduplicated in account scope. Conversations link to account/group/customer where known.
- Customer identities require explicit matching/confirmation; notes/tags and conversations preserve customer context without equating a WhatsApp phone to a client.
- Conversation participants, state history and assignments preserve responsibility and control changes. Support teams are existing assignment targets.
- Automation rules/profiles and knowledge articles retain versions; decision logs identify outcomes/sources; outbound rows retain delivery and idempotency state.
- Billing invoices reference customers and creators; payments reference invoices. Reversals retain the original row. Subscription events retain term changes.
- Memberships reuse `support_teams` and users; shifts and leave reference users. Notifications, saved replies and drafts are private to their user.
- Release edits retain snapshots and authors; only published notes are ordinary-user visible.

## Invariants and security

Foreign keys, unique indexes, positive-integer monetary checks and transactional locks protect important invariants. Account data is scoped by IDs, but there is no project/tenant key throughout the domain. Do not claim project isolation. Credentials use the existing encryption service. API response serialization excludes password/session secrets. SQL writes are parameterized.

## Migration practice

`1788400003000-InboxReading.ts` adds private `conversation_user_state` keyed by user/conversation (archive and manual-unread flags), and `message_user_reads` keyed by user/message (exact-message reads, no timestamp cutoff). Foreign keys cascade when their conversation/message is removed; users retain ordinary FK protection. An inbound non-system partial index supports unread lookups. Existing incoming messages initially count as unread for each user. Down migration removes these preferences/read receipts; production rollback requires preserving them first. These tables do not create project isolation or change conversation lifecycle/control state.

`1788400002000-CustomerDirectory.ts` adds immutable unique `customers.code`, generated from an owned sequence when omitted, plus nullable `country`, `serviceName` and `accountOwnerId` (user FK). Existing records receive codes without identity/history changes. `customer_import_receipts` retains actor, CSV fingerprint, created IDs and time for idempotent retries; raw CSV is not persisted. Removing these columns/receipts on rollback loses directory metadata and import replay history, so real rollback needs a preservation review.

`1788400001000-ShiftLifecycle.ts` adds cancellation actor/time/reason to existing shifts and an append-only `workforce_shift_events` table with actor and before/after snapshots. Active-overlap queries exclude cancelled records. Schedule changes use row/person locks. Reverting this migration removes lifecycle history and therefore needs data-preservation review on an installation with real changes.

Use explicit timestamped migrations and the existing migration command, with backups for real deployments. Do not reset a real database to obtain a green test. Isolated tests use the test Compose ports/database. Preserve audit/business history and evaluate rollback data loss before reverting an applied migration. The generated inventory includes source links; field declarations are not a replacement for the actual migration DDL or relation/index decorators.

## Go WhatsApp migrations (not yet applied in this phase)

- 1788400004000 adds channel_accounts.gatewayProvider, privately snapshots legacy account transport fields, clears legacy device/webhook state and changes the registered adapter to gowa. Account/customer/group/history IDs remain. The guarded down migration refuses to overwrite active new-provider device IDs.
- 1788400005000 adds outbound command/scheduled-for data, encrypted whatsapp_operations with creator/account/request-key uniqueness and private whatsapp_uploads. Operation results and uncertain outcomes remain attributable.
- 1788400006000 adds encrypted whatsapp_schedules, managed outbound schedule linkage and normalized messages.presentation for edits/deletions/reactions/polls. Original message bodies remain preserved. Schedule controls and exact occurrence idempotency are separate from delivery confirmation.
- 1788400007000 adds encrypted whatsapp_integrations, verified per-account Chatwoot conversation bindings and per-message delivery claims. Secrets and native provider snapshots have no generic operator read endpoint. Deleting an integration removes its credential/configuration and bindings while retaining the delivery ledger.

New private files currently use the existing local storage driver; external storage quotas/retention and CDN attachment policies require operational review. Rolling back these additive feature tables loses their new metadata and must not be applied casually to an installation with real usage.

- 1788400008000 adds generic per-account channel labels and timestamped label/chat associations. Native WhatsApp label events are normalized at the adapter; cached names and links survive raw-event retention. This release offers label display, not an invented provider editing API.

Cutover review: the transport migration cancels saved legacy QUEUED sends and marks legacy SENDING outcomes uncertain, retaining their requests/history for review. It never replays them automatically through the new phone binding. The future local-start script stops API/worker writers and the project-owned retired gateway before migration; it retains the legacy volume. These script/database actions have not been executed in this phase.
